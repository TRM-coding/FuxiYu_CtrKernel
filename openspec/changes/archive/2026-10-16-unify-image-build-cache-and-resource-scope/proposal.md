# Proposal

## Why

陈旧派发记录不能更新，平台注入变化未进入缓存判旧，导致已生成的新配方仍可能使用旧标签。镜像列表的资源范围还漏掉全局资源通配，并将授权名单混作“我的”归属。按已确认决策统一版本换代、关联身份和权限范围。

## What Changes

- 陈旧派发记录按同一机器、模板配对就地换代；后续未变化的配方稳定复用新版本。
- 最终配方的基础镜像、平台注入、业务片段和入口参与缓存一致性判断，同秒修改也不能复用旧制品。
- 保留旧容器版本留痕、镜像身份与授权关联，清退与实际换代路线冲突的缓存写入或失效分支。
- 默认列表、点鉴权与创建可用性统一处理资源通配；方法权限和模板状态仍独立生效。
- “仅看我的”严格按创建者过滤，不被资源通配或查看授权扩大。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `backend--table-machine-image`: 陈旧记录替换、配方一致性和派发留痕。
- `backend--table-images`: 稳定归属、平台注入影响缓存、资源通配与可见性。
- `backend--table-user-images`: 查看授权不等于所有权或方法授权。
- `backend--table-containers`: 保留旧构建留痕并使创建与恢复使用实际配方的版本。
- `backend--table-users`: 权限快照中区分方法权限与真实资源通配能力。

## Impact

影响 Ctrl 镜像解析、派发仓储、兼容数据库升级、权限快照与资源范围、容器创建和恢复，以及隔离回归测试。Node 继续按 Ctrl 下发标签查本机缓存；Web 按真实资源通配能力展示镜像管理范围。
