# Design

## Context

当前以 machine_id/image_id 定位缓存，标签由 image_id 与构建版本戳推导，旧容器依靠 image_id/last_build_at 识别实际版本。旧实现同时存在“记录永不改写”“编辑删除记录”“陈旧时生成新标签”三条不能闭环的路线，平台注入又没有进入判旧输入。

## Goals / Non-Goals

**Goals:** 最终配方与缓存版本一致；陈旧记录就地换代且后续命中稳定；秒级修改不碰撞；保持旧资源关联和历史容器标签有效；资源通配与方法权限独立。

**Non-Goals:** 不重建正在运行的容器，不清理宿主旧制品，不提供所有权转让；不让资源通配替代方法权限，不把授权查看视作创建者归属。

## Decisions

1. 缓存按最终 Dockerfile 的一致性判旧，覆盖四段配方；配方指纹是校验元数据，不是资源身份，也不直接替换现有标签格式。
2. 稳定键保留为 machine_id/image_id，解析实际配方时预留版本并更新同一配对记录，派发后确认同一组值。已有行使用数据库条件更新和影响行数判断，避免过期 ORM 对象覆盖其他会话的新版本；首次插入冲突后重读，无法收敛时拒绝分配。移除编辑全删缓存及“有行永不更换”的冲突路线。
3. 同秒不同内容必须分配可区分版本；保留旧 image_id/last_build_at 标签推导兼容。旧库未知配方的缓存不能未经验证直接标记为当前内容。
4. 创建和恢复都以实际下发配方解析版本；恢复历史正文时仍取当前平台注入，不能继续使用一个已缓存但不对应该组合的旧标签。新派发不改写旧容器的版本留痕。
5. 资源范围的唯一判定在 RBAC 服务，镜像默认列表和点鉴权共用；身份快照区分真实资源通配和展开后的方法权限，客户端不猜测。
6. mine_only 为创建者条件。授权名单只决定 CUSTOM 查看，不能扩大所有权筛选；资源通配不会覆盖显式筛选条件。

## Risks / Trade-offs

- 旧库没有配方校验元数据 → 兼容升级补齐可空字段，未知缓存按不能证明一致处理，实际新派发后稳定收敛。
- 秒级标签在快速修改时可能碰撞 → 版本选择需保证不同配方不复用旧标签，并验证连续改动和读写分离的边界。
- 旧容器标签不能随格式或当前缓存改动 → 保留历史推导规则，并测试旧容器、授权与恢复关联。
- 方法通配展开结果含 image:manage → 资源能力独立表达，避免前端错误放行全部资源。
- 解析时缓存不可读写 → 无法可靠排除标签冲突时拒绝请求；派发后确认失败仅告警，不回滚已被 Node 受理的创建。

## Migration Plan

沿用当前数据库升级载体补齐最少的一致性元数据；不删除镜像、容器、用户授权或宿主制品。旧缓存不能直接证明配方一致时生成安全的新版本，旧容器仍可识别。主规格的数据附录随最终模型更新。
