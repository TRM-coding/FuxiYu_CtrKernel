# Design

## Context

机器端口已有持久化及出站解析契约，缺口位于详情响应模型。注册流程则先在独立事务消费验证码，再调用另一个事务创建用户；普通 Register 还有默认组绑定步骤，需要一并核对成功边界。

## Goals / Non-Goals

**Goals:** 端口从数据库到响应、回填和展示一致；注册失败可重试；用户创建、必要身份关联及验证码单次消费以明确成功提交为边界。

**Non-Goals:** 不把默认端口固化进逐机记录，不改学校域、口令或登录策略，不拓展机器修改权限。

## Decisions

1. 详情 port 保留自定义数值或空配置，沿用现有出站端点解析。前端缺值显示平台默认语义，不猜测全局默认数值。
2. 将注册校验与用户写入组织为可共享事务的工作单元，验证码消费与用户成功创建一起提交；不能在返回校验失败时提交一个已消费标记。
3. 同码并发由数据库条件消费或等效的可靠事务机制控制；仅查询 consumed_at 或在进程内加锁不足以保证单次成功。
4. 必要默认组绑定遵守注册成功边界，审计不得将失败注册伪装成成功；现有非验证码建号行为保持兼容。

## Risks / Trade-offs

- 验证码可重试可能被重复提交 → 以有效期、未消费条件及单次成功约束控制，不因预检查失败浪费有效验证码。
- 事务组合影响普通建号 → 保留公共入口的现有校验与错误分类，并分别覆盖普通注册与验证码注册。
- 前端无法获知全局默认端口数值 → 明确展示默认配置语义，而不引入错误的固定端口。

## Migration Plan

优先复用现有字段和事务载体，不改变验证码哈希存储或机器端口空值含义。同步接口契约、失败重试回归及主规格，确认后归档。
